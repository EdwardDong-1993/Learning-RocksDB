# 01 | 为什么是 LSM-Tree？—— 从一次"数据库越写越慢"的故障说起

> 本专栏主线：**搞懂 RocksDB，用 C++ 造一个 mini 存储引擎**。
> 这是第一篇，没有任何代码，但它是后面 29 篇所有代码的"为什么"。

## 一、一次真实的故障

假设你刚入职一家互联网公司，负责一个用户资料服务。数据量不大，几千万条记录，每条记录就是一个 `(user_id → 用户资料的 JSON)`。团队选了最朴素的方案：**MySQL 存底，前面挂一层缓存**。

上线之初一切美好。三个月后，监控里出现了一条缓慢爬升的曲线——**磁盘写入延迟（ioutil）从 10% 一路涨到 85%**，写入 P99 延迟从 2ms 涨到 40ms（P99：把所有写入按耗时排序，99% 的请求都快于该值，用于衡量“最慢的那批请求”的指标，平均值会掩盖这样的长尾恶化）。DBA 翻遍参数也没找到配置问题，最后只留下一句："数据量到了，B+ 树的随机写撑不住了。"

这句话是什么意思？为什么"数据量到了"会"随机写撑不住"？要回答它，我们得先退回到最原始的问题。

## 二、存储的三个基本问题

不管多复杂的存储系统（MySQL、Redis、RocksDB、Kafka），本质上都在回答三个问题：

1. **写到哪？** —— 数据以什么形式放在什么介质上
2. **怎么读回来？** —— 给我一个 key，如何快速定位到它的 value
3. **怎么保证不丢？** —— 断电、崩溃之后，数据还能不能完整回来

本专栏的全部内容，就是围绕这三个问题在磁盘这个特定介质上的展开。而在磁盘上回答这三个问题，绕不开一个物理事实。

## 三、磁盘的真相：顺序写和随机写是两种世界

如果你对存储是零基础，请先记住这一组数字（SSD 与 HDD 数量级不同，但结论一致）：

| 操作 | 机械硬盘 (HDD) | SSD |
|---|---|---|
| 顺序写 1MB | ~几十 MB/s | ~GB/s 级 |
| 随机写 4KB | ~几百次/秒 | ~几十万次/秒 |
| **差距** | **3 个数量级以上** | **数倍到数十倍（且写放大更致命）** |

> 表格里的两种口径不同：顺序写用**吞吐量**（MB/s，管道粗细），随机写用 **IOPS**（次/秒，离散请求处理能力）——这是存储行业规格书的原生表达。两者可以换算同意：**随机写吞吐 = IOPS × 块大小**。一上面 HDD 数据为例：150 IOPS × 4KB ≈ 0.6 MB/s，对比顺序写 ~200 MB/s，差距约 300 倍。SDD 没有机械寻道，随机 IOPS 高达几十万，换算后随即吞吐已接近顺序——它的随机写代价主要隐藏在 NAND 写放大与后台 GC 中（第5章起展开）

对 HDD 而言，随机写要付出磁头寻道 + 旋转等待的代价，一次约 10ms；而顺序写只是"接着往后写"。**顺序写几乎是免费的，随机写是昂贵的**——这是磁盘世界最重要的物理定律。

> 你之后会在本专栏里反复看到这条定律的影子：LSM-Tree 的一切设计，都是在"把随机写变成顺序写"。

现在，带着这个定律，我们看第一个主流方案：B+ 树。

## 四、方案一：B+ 树——"就地更新"的代价

B+ 树是你可能听说过的 MySQL/InnoDB、MongoDB 的核心结构。用一张图描述它（可以想象成图书馆的分区分层目录）：

```
                    [ 根节点 ]
                   /    |    \
            [ 内部节点 ] [ 内部节点 ]        ← 只存"路标"（key 范围）
             /    \        /    \
        [叶子页] [叶子页] [叶子页] [叶子页]  ← 真正存数据，页内有序
        k1..k100 k101..k200 ...
```

- 每个节点是固定大小的**页**（如 16KB），页内 key 有序，支持二分查找
- 查找：从根往下走 2~4 层，每次读一个页 → **读性能极好，这是 B+ 树的天下**
- **写入**：定位到叶子页 → **在页内原地修改**（插入、更新、删除都是"改"这一页）

问题就出在"原地修改"三个字上。写入 `user_9527 = {...}` 时：

1. 这条记录可能落在磁盘上**任意位置**的某个叶子页里（取决于 key 的排序位置）
2. 你必须先把这个页从磁盘读上来（随机读）
3. 改完再写回去（**随机写**）
4. 更糟：数据越插越多，页会分裂、树会长高、索引页也要跟着改——**一次逻辑写入，触发多次物理随机写**

这就是故障的答案：**数据量越大、key 越随机，写入位置越分散，随机写越多**。B+ 树用"就地更新"换来了极致的读性能，代价是写。

由此引出本专栏最重要的概念之一：

> **写放大（Write Amplification, WA）**：你写 1 字节，磁盘实际写了 N 字节。B+ 树的 WA 来自页原地改写 + 页分裂。

那能不能换一种思路——**不就地更新，永远只往后追加**？

## 五、方案二：LSM-Tree——"只追加，不修改"

LSM-Tree（Log-Structured Merge-Tree，日志结构合并树）的核心思想一句话就能说完：

> **把所有写操作变成磁盘上的顺序追加，读的时候再从新到旧把数据"找"回来。**

它的写路径长这样（这就是 RocksDB 的骨架图，后面 29 章都在填这张图）：

```
 写入 Put("user_9527", data)
        │
        ▼
   ① WAL 追加         ② MemTable（内存跳表，有序）
   ─────────────►     ┌────────────────────┐
   顺序写日志，         │ user_0001 | v3     │  ← 先写日志再写内存，
   崩溃后用它恢复       │ user_0234 | v1     │    写入即返回（快！）
                       │ user_9527 | v2     │
                       └────────┬───────────┘
                                │ 内存写满（如 64MB）
                                ▼
   ③ Flush：整块内存排序数据，一次性顺序写成 SST 文件
   ┌────────────── SST 文件（不可修改！）──────────────┐
   │ user_0001 | v3   user_0234 | v1   user_9527 | v2 │  内部有序
   └───────────────────────────────────────────────────┘
```

三个关键角色，先混个眼熟（后续章节都会亲手实现）：

- **WAL**（Write-Ahead Log）：写入前先顺序追加一条日志。作用是"还没落盘的内存数据，崩了也能救回来"。回答了"怎么保证不丢"。
- **MemTable**：内存里的有序结构（跳表）。写入只动它，速度近似内存写入。回答了"写到哪（第一站）"。
- **SST**（Sorted String Table）：内存写满后，整块**顺序**刷成一个不可修改的磁盘文件。之后不再动它。

注意一个反直觉但极其重要的设计：**SST 文件一旦生成，永远不修改**。更新 `user_9527`？不找到旧文件改它，而是往 MemTable 写一条更新的记录。删除？也不是抹掉旧数据，而是写一条"墓碑"（tombstone）标记。

> 于是磁盘上可能同时存在 `user_9527` 的多个版本：`v1（SST-003）`、`v2（SST-011）`。读的时候取**最新的**那条即可。

### 写入的完整旅程

`Put("user_9527", v3)` 一次写入的全部开销：

1. 追加一条 WAL 日志（**顺序写**）
2. 插入内存跳表（**内存写**）
3. 返回成功

没有随机写。磁盘上只有"往后追加"这一个动作。这就是 LSM 对"磁盘物理定律"的投降式顺应——**你说随机写贵，我就一条都不做**。

对比一下两种结构的气质：

| | B+ 树 | LSM-Tree |
|---|---|---|
| 写 | 就地更新，随机写 | 追加 + 顺序刷盘 |
| 读 | 树上直达，最多 2~4 次页读 | 新到旧逐层查找，可能查多个文件 |
| 气质 | 为读而生 | 为写而生 |
| 典型代表 | InnoDB、MongoDB | RocksDB、LevelDB、HBase、TiKV、Cassandra |

## 六、天下没有免费的午餐：读放大

LSM 用"写得很爽"换来了一个新问题——**读的时候，数据可能散落在任何地方**：

- MemTable 里？（在内存，最快）
- 最新的 SST 里？
- 更老的 SST 里？甚至同一个 key 有 5 个版本分散在 5 个文件里？

最坏情况：内存查一次 + 每个 SST 文件都查一次。这就叫**读放大（Read Amplification, RA）**——一次逻辑读，放大成 N 次物理读。

而且 SST 只增不减，磁盘很快会被旧版本和墓碑塞满——这是**空间放大（Space Amplification, SA）**。

LSM 的第三块拼图，就是解决这两个问题的：**Compaction（合并压缩）**。

```
 后台线程（Compaction）：
 ┌ SST-A ┐   ┌ SST-B ┐      归并排序去重
 │ k1 v1  │ + │ k1 v2 │  ─────────────►  ┌ 新 SST（只留最新版本）┐
 │ k2 v1  │   │ k3 v1 │    顺序读写        │ k1 v2  k2 v1  k3 v1  │
 └────────┘   └───────┘                   └───────────────────────┘
```

Compaction 把多个 SST 归并成新的 SST（**顺序读 + 顺序写**），顺带扔掉旧版本和过期墓碑。它是在后台慢慢做的，不阻塞前台写入——这就是 LSM 的全部权衡艺术：

> **写入永远顺序追加；读放大和空间放大，交给后台 Compaction 慢慢还债。**

**三大放大（写放大 / 读放大 / 空间放大）是此消彼长的三角**，第 17 章我们会专门定量分析它们，RocksDB 几十个调优参数，本质上都是在调这个三角。

## 七、RocksDB：LSM 的工业级集大成者

理解了 LSM，RocksDB 是什么就好说了：Facebook（Meta）基于 Google LevelDB 二次开发的开源**嵌入式 KV 存储引擎**。注意"嵌入式"——它不是独立的数据库服务，而是一个**链接进你程序的 C++ 库**：

```cpp
rocksdb::DB* db;
rocksdb::Options opts;
rocksdb::DB::Open(opts, "/data/mydb", &db);
db->Put(rocksdb::WriteOptions(), "user_9527", json);
```

它在你进程里，就是你的"私人数据库内核"。因为极高性能 + 极强可定制性，它成了工业界的地基：TiKV（TiDB 存储层）、MyRocks（MySQL 引擎替换）、Flink 状态后端、Fbase/Pika 等众多国产分布式存储、以及各类消息/索引系统，底下都是 RocksDB。

它把 LSM 的每个部件都打磨到了工业水准：列族、多线程 Compaction、分区索引、布隆过滤器、快照、事务、备份……这也正是本专栏每一章的"对照答案"——**我们每实现一个玩具部件，都会回来看 RocksDB 把它做到了什么程度**。

## 九、思考题（下一篇的伏笔）

1. LSM 写入要先写 WAL 再写 MemTable——这两步反过来行不行？为什么？（提示：崩溃发生在两步之间）
2. 同一个 key 的 v1 在旧 SST、v2 在新 SST，读的时候怎么知道该用哪个？需要一个什么机制？
3. 墓碑（删除标记）如果永远留着，会带来什么？如果 Compaction 时把它扔了，又会出什么问题？（这是 LSM 最经典的坑之一，第 20 章见）
