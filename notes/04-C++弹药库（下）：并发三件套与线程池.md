## 一、上篇思考题解答

**Q1：删掉 `explicit operator bool()`，`if (fd)` 还能编译吗？**

能，而且更危险。`fd_` 是 `int`，`if (fd)` 会走 **int→bool 隐式转换**：非 0 即真，**-1 也算真**！于是 `FdGuard(-1)`（不持有任何 fd）在 `if` 里被当成"有效"。`explicit` 的妙处在于：语境转换（`if`、`&&`）仍然放行，但 `int x = fd;`、`fd + 1` 这类误用被编译器拦下。**自定义转换运算符，永远加 `explicit`**。

**Q2：`shared_ptr` 的引用计数为什么必须原子？**

拷贝 `shared_ptr` 是 `++count`，析构是 `--count`。两个线程各自持有一个 `shared_ptr` 实例（指向同一控制块）同时析构时，就是两个线程同时 `--count`——非原子的读-改-写会丢失一次递减，计数永远到不了 0（泄漏），或提前到 0（双释放）。这就是上一篇说"引用计数不是免费的"的准确含义：免费的是语义，付费的是原子指令。

**Q3：`std::move(a)` 之后还能用 `a` 吗？**

标准答案：**处于"有效但未指定"状态**——可以析构、可以赋新值，但不能假设它的内容。`unique_ptr` 被移动后保证为空（契约明确）；`std::string`、`vector` 被移动后通常是空的（但那是实现恩惠，不是承诺）。RocksDB 里 `std::move(memtable)` 之后继续使用，要么依赖类型契约（移动后状态明确），要么紧跟着赋新值——是否安全看类型，不能靠直觉。

## 二、存储引擎为什么必须多线程

回想第 1 章的 LSM 骨架图，有一个角色没展开讲：**Compaction 是谁在跑？**

- 前台写入线程在 MemTable 里奋笔疾书
- 后台线程在做 SST 归并（可能是几百 MB 的顺序读写，持续数秒）
- 两者同时发生，操作的是共享的元数据（"磁盘上有哪些 SST 文件"这张表）

**前台请求延迟以微秒计，后台任务以秒计，绝不能让写入等 Compaction。**所以"多线程 + 共享数据"从架构上就躲不开。RocksDB 更激进：Compaction 本身也多线程并行（`max_background_compactions`、`max_subcompactions`），一个 8GB 的合并任务切成 N 段同时干。

并发编程的工具箱，最核心的是三件套：**mutex（互斥）、condition_variable（通知）、atomic（免锁原子操作）**。

## 三、mutex：共享数据的门卫

多个线程同时读写同一个 `std::queue`，会直接撕裂数据结构（UB）。规则很简单：**共享可变数据，必须锁**。

```cpp
std::mutex mu;
std::queue<Task> tasks;

// 生产者
{
    std::lock_guard<std::mutex> lk(mu);   // ① 构造即加锁
    tasks.push(task);
}                                         // ② 离开作用域自动解锁

// 消费者
{
    std::lock_guard<std::mutex> lk(mu);
    if (!tasks.empty()) { auto t = tasks.front(); tasks.pop(); }
}
```

`std::lock_guard` 是第 3 章 RAII 的直接应用：**锁也是一种资源**，忘了解锁是死锁，忘不了锁的存在才是正确的。注意 `std::unique_lock` 与 `lock_guard` 的分工：前者支持中途 `unlock()`/配合条件变量，后者纯粹"作用域即锁的范围"，能用 `lock_guard` 就用 `lock_guard`。

一个铁律先立在这里：**判断"要不要加锁"的依据是数据，不是代码**。凡被多线程触碰的可变数据，每一条访问路径都得在锁内——漏一条就是数据竞争（C++ 里是 UB，不是"偶尔出错"）。

## 四、condition_variable：让线程"睡着等活"

只有 mutex 的消费者线程会陷入忙轮询：锁上→队列空→解锁→立刻再锁……CPU 空转。需要的是"没活干就睡觉，有活干被叫醒"：

```cpp
std::condition_variable cv;
std::unique_lock<std::mutex> lk(mu);

cv.wait(lk, [] { return !tasks.empty(); });  // 谓词版 wait
// 醒来时：已重新持锁，且谓词为真
```

`wait` 的完整动作是：**放锁 → 睡眠 → 被唤醒后重新抢锁 → 检查谓词 → 不满足继续睡**。两个容易栽的坑：

1. **虚假唤醒（spurious wakeup）**：操作系统允许"没人叫你，你也醒了"。所以必须用谓词版 `wait`，醒来重查条件——写成裸 `wait()` 再手动 `if` 判断，虚假唤醒就穿过去了。
2. **唤醒丢失**：先 `notify` 再 `wait`，通知就蒸发了。谓词检查在持锁状态下进行，条件不满足绝不会睡过去——这依赖"改条件"和"notify"的顺序约定，实战代码里看我们的 `submit`：锁内改队列、锁外 notify。

生产者一侧：

```cpp
{
    std::lock_guard<std::mutex> lk(mu);
    tasks.push(task);
}
cv.notify_one();   // 叫醒一个睡眠者
```

## 五、atomic：小数据的免锁快车道

计数器、标志位这类一个字的共享数据，上 mutex 太重——锁的开销可能比被保护的操作贵十倍。`std::atomic<int>` 用 CPU 原子指令保证"读-改-写"不可分割：

```cpp
std::atomic<int> done{0};
++done;        // 原子自增，多线程并发也不丢计数（对比上篇思考题 Q2）
done.load();   // 原子读

std::atomic<bool> stopping{false};
stopping.store(true);
```

选型直觉：**数据小（一个标量）、操作简单 → atomic；数据结构复杂 → mutex**。我们的线程池里 `done` 计数用 atomic，任务队列用 mutex，各得其所。

## 六、实战：ThreadPool 全文精读

零件齐了，组装。`src/thread_pool.h`（约 60 行，Compaction 后台线程的地基）：

```cpp
class ThreadPool {
public:
    explicit ThreadPool(size_t thread_num) {
        workers_.reserve(thread_num);
        for (size_t i = 0; i < thread_num; ++i) {
            workers_.emplace_back([this] { worker_loop(); });  // 启动 N 个工人
        }
    }
    ~ThreadPool() { shutdown(); }          // RAII：析构收编所有线程

    ThreadPool(const ThreadPool&) = delete;
    ThreadPool& operator=(const ThreadPool&) = delete;

    void submit(std::function<void()> task) {
        {
            std::lock_guard<std::mutex> lk(mu_);
            if (stopping_) return;
            tasks_.push(std::move(task));
        }
        cv_.notify_one();                  // 锁外通知，减少被唤醒者撞锁
    }

private:
    void worker_loop() {
        for (;;) {
            std::function<void()> task;
            {
                std::unique_lock<std::mutex> lk(mu_);
                cv_.wait(lk, [this] { return stopping_ || !tasks_.empty(); });
                if (stopping_ && tasks_.empty()) return;   // 关门且清空 → 退休
                task = std::move(tasks_.front());
                tasks_.pop();
            }                               // ← 执行任务前放锁！
            task();
        }
    }

    void shutdown() {
        {
            std::lock_guard<std::mutex> lk(mu_);
            if (stopping_) return;
            stopping_ = true;
        }
        cv_.notify_all();                  // 广播：都醒醒，该下班了
        for (auto& t : workers_)
            if (t.joinable()) t.join();    // 等每个工人真正退出
    }
    // 成员：workers_ / tasks_ / mu_ / cv_ / stopping_
};
```

四个值得咀嚼的设计点：

1. **析构即 join**：`~ThreadPool` → `shutdown()` → `join()`。忘 join 的线程在进程退出时是 UB，RAII 一并解决（第 3 章的 `FdGuard` 管一个 fd，这里管 N 个线程——同一思想的规模放大）。
2. **退出条件 `stopping_ && tasks_.empty()`**：关门时**队列里剩余的任务会被执行完**，而不是扔掉。为什么这样设计？对存储引擎，队列里可能躺着"刷 WAL"这类任务，扔了就是丢数据（思考题 Q1）。
3. **取任务后放锁再执行**：`task()` 可能耗时数秒（想象一个 Compaction），如果持锁执行，其他工人全堵在门口，线程池退化成单线程。
4. **`notify_one` / `notify_all` 的分工**：来一个活叫一个人；关门时叫所有人（每个人都要醒来判断自己是否退休）。

### 冒烟测试

`main.cpp` 里提交 8 个任务（各睡 50ms）到 4 线程的池子，本机真实输出：

```
=== 线程池冒烟测试: 8 个任务 / 4 个工作线程 ===
  任务 2 完成 (第 1 个)
  任务 1 完成 (第 2 个)
  任务 0 完成 (第 3 个)
  任务 3 完成 (第 4 个)
  任务 4 完成 (第 5 个)
  任务 6 完成 (第 6 个)
  任务 5 完成 (第 7 个)
  任务 7 完成 (第 8 个)
完成顺序交错 → 任务确实被 4 个线程并发执行
```

读一下这张输出：**前 4 个任务几乎同时完成**（4 个工人各领一个，50ms 后齐刷刷交付），随后 4 个任务再各领一个。完成顺序交错（2,1,0,3...）正是并发调度的指纹——如果 50ms × 8 = 400ms 串行，前 4 个不会挤在同一时刻完成。

## 七、RocksDB 对照

- RocksDB 有自己的线程池实现（`util/threadpool_imp.cc`），结构与我们惊人一致：任务队列 + 条件变量 + RAII 生命周期，只是多了优先级队列（Flush 任务优先级低于 Compaction）、动态线程数
- 后台线程的总入口在 `DBImpl::MaybeScheduleFlushOrCompaction`——第 23 章读源码时，你会认出今天写的每一个零件
- 一个有品味的细节：RocksDB 把 "任务队列" 从 `std::queue` 换成了带优先级的结构，但 `mutex + cv` 的骨架从未变过——**底层模式是稳定的，变化的是策略**

## 八、本章小结

- `mutex` + `lock_guard`：共享可变数据的门卫，判断依据是"数据"不是"代码"
- `condition_variable` 谓词版 `wait`：睡眠等活，防虚假唤醒
- `atomic`：单标量数据的免锁快车道
- `ThreadPool`：三件套的集成应用，RAII 管线程生命周期，后续 Compaction 直接复用
- 至此 C++ 弹药库备齐（RAII/智能指针/移动 + 并发三件套），从下一篇起开始造引擎

## 九、思考题

1. `shutdown()` 想改成"立即丢弃剩余任务"（不等队列清空），要动哪几行代码？对存储引擎，"丢弃队列里的任务"可能丢掉什么——由此推出引擎关闭时的正确顺序应该是什么？
2. `worker_loop` 里如果把 `task()` 挪到锁内执行，最坏会发生什么？除了"变慢"，有没有可能出现**死锁**？（提示：任务里又 `submit` 了一个新任务）
3. `stopping_` 只是个普通 `bool`，为什么不需要 `std::atomic<bool>` 就没有数据竞争？（提示：它的每一次读写都发生在哪个锁的保护下？）
