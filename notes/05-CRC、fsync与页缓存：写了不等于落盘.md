# 05 | CRC、fsync 与页缓存：写了 ≠ 落盘了

> 上篇思考题解答 → 一次 `write()` 背后的完整旅程 → 断电撕裂与位翻转 → 动手：引擎第一个真模块 WAL（record 格式 + CRC + 崩溃恢复）。弹药库至此收官，引擎正式开张。

## 一、上篇思考题解答

**Q1：`shutdown()` 改成"立即丢弃剩余任务"要动哪里？对存储引擎意味着什么？**

退出条件 `if (stopping_ && tasks_.empty()) return;` 改成 `if (stopping_) return;`——醒来发现关门就撤，不干剩下的活。对存储引擎，队列里可能躺着"WAL 刷盘"、"MemTable 落盘"这类任务，丢弃 = 丢数据。由此推出引擎的正确关机顺序：**先停止接收新写入 → 把 WAL 和 MemTable 完整落盘 → 最后才关线程池**（保证队列排干）。我们第 30 章收官时会亲手实现这个顺序。

**Q2：`task()` 挪到锁内执行会怎样？**

轻则线程池退化成单线程（一人干活，众人排队）。重则死锁：任务 A 持锁执行中又提交任务 B 并**等待 B 完成**（join / 条件等待），而 B 永远抢不到那把锁——互等，锁死。所以铁律是：**拿数据要锁，干活放锁**。

**Q3：`stopping_` 为什么不用 atomic？**

数据竞争的定义是"至少一个写、且无同步"。而 `stopping_` 的每次读写（`wait` 谓词、`submit` 检查、`shutdown` 置位）都发生在 `mu_` 持有期间——锁提供了 happens-before 关系，可见性和原子性都已被保证。`atomic` 是给"锁外访问"的数据准备的。**给已受锁保护的数据加 atomic，是药不对症**。

## 二、一次 `write()` 的完整旅程

第 2 章我们被页缓存骗过一次，这次正面拆开它。你以为的写入：

```
程序 write()  ─────────────►  磁盘
```

真实的写入：

```
程序 write() ──► 页缓存(Page Cache, 内存) ──[内核择机异步]──► 磁盘
                没错，write() 返回时，      ↑
                数据大概率只在内存里!        断电 = 全部蒸发
```

`write()` 返回成功，只代表数据进了**页缓存**。内核会攒一批"脏页"择机刷盘（writeback）。于是在"write 返回"到"真正落盘"之间存在一个窗口——窗口内断电，数据无声蒸发。**从引擎的视角：进程崩溃不丢数据（页缓存由内核接管，还活着）；机器断电才丢数据（页缓存蒸发）**。

把数据钉到磁盘的 API：

- `fsync(fd)`：数据 + 文件元数据（大小等）全部落盘
- `fdatasync(fd)`：只求数据落盘，元数据能省则省——快一点，WAL 场景的常规选择

它们的代价：每次 `fdatasync` 是一次真实落盘，毫秒级。**每条日志 sync 一次 = 吞吐坍塌；从不 sync = 崩机丢数据**。这是 WAL 的头号权衡，RocksDB 的解法（组提交、可配置 sync 间隔）第 23 章展开。

## 三、断电的两种破坏形态

假设 WAL 里连续写了 1000 条记录，断电时第 1000 条只落了一半：

**形态一：撕裂（torn write）**——最后一条记录物理上不完整。这几乎是"良性"的：恢复时读到一条不完整的记录，丢弃即可（LevelDB 的 log 就是这个语义）。

**形态二：位翻转（bit rot / 静默损坏）**——盘上的位自己翻错了（电磁干扰、固件 bug）。撕裂靠"读不满"发现，位翻转**读得满满当当，内容是错的**——没有额外校验机制，它会直接混进你的数据里。这就是 CRC 的战场。

> CRC 的直觉版原理：把数据当成一个超长的二进制数，用一个约定多项式做"带余除法"，余数就是校验码，附在数据后面。读的时候重算一遍，余数不一致 = 数据被动过。它能可靠拦截所有 1~2 位翻转、所有奇数位翻转、以及绝大多数突发错误；拦不住的是"恰好构造出相同余数的恶意篡改"——那是对抗场景，得换密码学哈希（SHA 等）。磁盘位翻转这种非对抗性错误，CRC 是性价比之王。

## 四、动手：WAL 雏形

### record 格式设计

```
+-------------+------------+---------------------+
| length (4B) | crc32 (4B) | payload (length B)  |
+-------------+------------+---------------------+
```

`length` 告诉读方"payload 有多长"，`crc32` 守门 payload。对比真实世界：LevelDB/RocksDB 用 **7 字节头**（crc 4 + len 2 + type 1）且按 **32KB 定长 block 分段**，payload 大于块就拆成 FIRST/MIDDLE/LAST 多条——为了读写对齐友好。我们先不分段，语义立住即可。

### 写入：拼好整条，一次 `write()`

```cpp
bool WalWriter::append(const std::string& payload) {
    uint32_t len = static_cast<uint32_t>(payload.size());
    uint32_t crc = crc32(payload.data(), payload.size());

    std::string rec;
    rec.reserve(kHeaderSize + payload.size());
    rec.append(reinterpret_cast<const char*>(&len), 4);
    rec.append(reinterpret_cast<const char*>(&crc), 4);
    rec.append(payload);

    ssize_t n = ::write(fd_.get(), rec.data(), rec.size());
    return n == static_cast<ssize_t>(rec.size());
}
```

两个设计点：头和 payload **拼成一次 `write()`**——顺序追加是 LSM 命根子，且尽量缩小"半个头先落盘"的窗口；写完不自动 sync（`sync()` 单独暴露给上层），调用方决定何时付落盘的代价。

### 恢复：三道关卡，逐条校验

```cpp
for (;;) {
    ssize_t n = ::read(guard.get(), header, kHeaderSize);
    if (n == 0) break;                                  // 关卡0: 干净 EOF, 日志完整
    if (n != static_cast<ssize_t>(kHeaderSize)) break;  // 关卡1: 头撕裂 → 停
    ...
    if (len > kMaxPayload) break;                       // 关卡2: 头被写坏, 长度疯狂 → 停
    ...读满 payload, 读不满 → 停...                       // 关卡3: payload 撕裂 → 停
    if (crc32(payload.data(), payload.size()) != crc) break;  // 关卡4: 位翻转 → 停
    out.push_back(std::move(payload));
}
```

策略是"**就地停止**"：尾部不完整/损坏记录之后的日志全部放弃。另一个选项是"跳过坏的继续读"——但损坏点之后的日志还能信吗？LevelDB 的选择和我们一致：停。

## 五、三场景实测

`main.cpp` 写了三个剧本，本机真实输出：

```
=== WAL 雏形: 写入 / 崩溃恢复 / CRC 守门 ===
① 正常写入 5 条, 重放得到 5 条
② 最后一条只写了 3 字节(模拟断电), 重放得到 4 条 → 撕裂记录被丢弃
③ 第 2 条 payload 被翻转 1 bit, 重放得到 1 条 → 重停在损坏记录处
```

- 剧本②用 `truncate()` 把文件拦腰砍在第 5 条中间，模拟断电撕裂——前 4 条完好恢复
- 剧本③翻开文件，把第 2 条 payload 中间的一个字节 `^= 0x20`——数据**读得满满当当，内容是错的**，靠 CRC 拦下。注意结果只有 1 条：重停在第 2 条处，第 3~5 条虽然物理完好也不再读——"就地停止"策略的直接体现

至此，第 1 章问题 3（"怎么保证不丢"）有了第一块拼图：**崩溃后，WAL 重放能拿回断电前已 sync 的全部记录，外加至多一条撕裂（被丢弃）**。

## 六、RocksDB 对照

打开 `rocksdb/db/log_writer.h`，你会看到几乎同构的逻辑，差异都在工程细节：

| 维度 | 我们的雏形 | RocksDB/LevelDB |
|---|---|---|
| 头 | 8B（len 4 + crc 4） | 7B（crc 4 + len 2 + type 1） |
| 组织 | 一条 record 任意长 | 32KB 定长 block 分段，跨块拆 FIRST/MIDDLE/LAST |
| 字节序 | 本机序（`memcpy`） | 显式小端编解码（可移植） |
| CRC | 32 位 | crc32c（Castagnoli 多项式，SSE4.2 硬件加速） |
| 头的校验 | 无（靠 len 合理性兜底） | **头也在 CRC 覆盖内**（用"长度点预跳"技巧） |
| sync 策略 | 手动调 `sync()` | 按 WriteOptions：每条 sync / 组提交攒批 sync |

最后一行值得多说一句：`WriteOptions().sync == true` 时每条写完就 fdatasync（最安全最慢）；默认 false 时攒一批一起 sync，断电最多丢"最近一批"——**用可控的丢失窗口换吞吐**。生产系统在两者之间按业务语义选档，没有免费午餐。

## 七、本章小结

- `write()` 只到页缓存，`fdatasync` 才落盘；**进程崩溃不丢、断电丢**
- 断电两形态：撕裂（读不满，易处理）、位翻转（读满但错，CRC 拦截）
- WAL 雏形落地：8B 头 + CRC + 顺序追加 + "就地停止"式恢复，三场景实测通过
- 至此五篇弹药库收官：从下一篇起进入第二篇实战——**跳表与 MemTable**
