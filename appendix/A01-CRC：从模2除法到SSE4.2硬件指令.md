# A01 | CRC：从模 2 除法到 SSE4.2 硬件指令

> 触发来源：`notes/05` 只给了 CRC 的"除法"直觉和一段逐位实现。本篇把数学原理、检测能力的证明思路、工程加速路线、CRC-32 与 CRC-32C 的选型逻辑讲透。不含代码。

## 一、CRC 是用来做什么的

**CRC（Cyclic Redundancy Check，循环冗余校验）是一种错误检测码**：对任意长度的数据，计算出一个固定位数的校验值（比如 32 位）附在数据尾部；拿到数据的一方重算一遍、与附带的校验值比对——不一致，即数据在传输或存储途中发生了意外损坏。

它保护的是**随机性损坏**（电磁噪声、位翻转、介质老化），不防御恶意篡改（那是密码学哈希的领域，见第十节）。它离你比想象中近：

| 场景 | 用 CRC 防什么 |
|---|---|
| 以太网帧尾的 FCS、Wi-Fi 帧 | 网线/无线上的传输噪声 |
| ext4 / Btrfs / ZFS 的数据与元数据校验 | 磁盘介质的位翻转、静默损坏 |
| RocksDB 的 WAL record、SST block | 落盘/回读途中的损坏（ch05 的"守门"） |
| zip / PNG 等压缩格式的段校验 | 文件损坏 |

一句话：**数据凡要经过"不可信通道"（网线、磁盘、总线），就需要一个廉价可靠的错误哨兵——CRC 是经过六十多年工业淬炼的标准答案**。它为什么可靠、为什么便宜，就是接下来十节的内容。

## 二、模 2 算术：加减都是异或

CRC 的全部数学建立在"模 2 运算"上：**不进位的加、不借位的减，都等价于异或（XOR）**。

```
  1011        1011        1011
+ 1100      - 1100     XOR 1100
------      ------      ------
  0111        0111        0111     ← 三种运算结果完全相同
```

没有进位的世界里，"加"和"减"是同一个运算，除法也因此变得简单：不需要比大小、不需要借位，只需要在"当前最高位是 1"时拿除数去 XOR。

## 三、手算一个完整的 CRC

用 4 位 CRC 做例子（CRC-32 的完整同构缩小版）。约定：

- 生成多项式 **G = 10011**，即数学上的 x⁴ + x + 1
- 待保护的消息 **M = 110101101**（9 位）

**发送方的三步**：

**第 1 步：补零**。消息左移 CRC 位数（4 位），即末尾追加 4 个 0，得被除数：

```
110101101 0000        ← M 后面接 4 个 0（数学上就是 M × x⁴）
```

**第 2 步：模 2 长除法**。用 10011 去除，规则只有一条：部分余数最高位是 1 就商 1 并 XOR 除数，是 0 就商 0 直接移位。完整竖式：

```
1101011010000   ÷  10011

 1101011010000
 10011···                ← 最高位是 1，XOR 除数
 ---------
 0100111010000           ← 首位已消为 0
 ·10011··                ← 移到下一位 1，再 XOR
 ---------
 0000001010000           ← 连续 5 位全 0，继续右移
 ·····10011·             ← 第 7 位是 1，XOR
 ---------
 0000000111000
 ·······10011            ← 第 8 位是 1，XOR
 ---------
 0000000001111           ← 剩余位数不足 5，除法结束
              ↑↑↑↑
              余数 = 1111   ← 这就是 4 位 CRC
```

**第 3 步：附加余数**。发送的完整帧 = 消息 + CRC：

```
110101101 1111
```

**接收方**：对整个 13 位帧做同样的除法。为什么余数必然是 0？因为

```
(M × x⁴) mod G = CRC
⇒ M × x⁴ + CRC  ≡  0  (mod G)      ← 模 2 下加 = 减
```

发送帧正是 M × x⁴ + CRC 的位串形式——**它在数学上就是 G 的倍数**。传输若引入任何损坏，接收到的就是"G 的倍数 + 错误位串"，除一下余数非零，损坏暴露。

## 四、检测能力的证明思路

把传输错误也写成多项式 **E(x)**（哪些位翻转，哪些位置就是 1）。检测条件归结为一句话：

> **E(x) 不能被 G 整除 → 错误必被发现。**

用这个视角逐条推（这是教科书结论的来历，不是记忆）

**① 单比特错必检**。E(x) = xᵏ。只要 G 至少含两个非零项（有常数项 x⁰），xᵏ 这种"单项式"永远除不尽它。所有 CRC 都满足。

**② 奇数个比特错必检**。E(x) 含奇数项。若 G 是 (x+1) 的倍数，则 E(x) 除以 G 余数必非零——因为 x+1 能整除的多项式，其二进制系数必有偶数个 1。CRC-32 的多项式 0x04C11DB7 恰有 14 个非零项（偶数），正是 (x+1) 的倍数，所以**任何奇数位翻转 100% 被检出**。

**③ 长度 ≤ n 的突发错误（burst）必检**。突发错 = 首尾各一个 1、跨度不超过 n 位的多项式 E(x) = xʲ·B(x)，B 的次数 < n。次数低于 n 的 B(x) 不可能被 n 次的 G 整除。所以 **CRC-32 检出所有 ≤ 32 位的突发错误**——磁盘/网络错误常呈"连续几位受损"的突发形态，这是 CRC 对存储介质特别有效的原因。

**④ 双比特错**。E(x) = xʲ(xⁱ⁻ʲ + 1)，漏检需要 G 整除 xⁱ⁻ʲ + 1，这要求两错误位距离是 G "指数"的倍数（数量级 2³²）。帧长远小于此 → 实际 100% 检出。

**⑤ 其余一切**：错误模式恰使 E(x) 是 G 的倍数的概率 ≈ 2⁻³²。这就是"每 40 亿次随机损坏漏检一次"的来历。

**CRC 检测不了什么**：① 恶意构造的碰撞（攻击者可反向求出使余数为 0 的篡改——对抗场景必须换密码学哈希）；② E(x) 恰为 G 倍数的随机巧合（概率 2⁻³²）。

## 五、反射式 CRC 与 0xEDB88320 的来历

你可能注意到两个"标准多项式"：**0x04C11DB7**（CRC-32）和 **0xEDB88320**（代码里常见的那个）。后者就是前者的**位反转**（bit-reverse）：

```
0x04C11DB7 = 00000100 11000001 00011101 10101111
位反转后   = 11110101 10111000 10000011 00100010 = 0xEDB88320
```

为什么会有"反射式"？历史原因是**串行硬件**：UART 等串行线路按"低位先发"传输，硬件逐位计算时天然按反射位序处理。于是反射式 CRC 成为软件与协议的常见默认（zlib、PNG、以太网 FCS 均是）。数学结果上，反射式与非反射式只是"镜像世界"的两种实现，检测能力相同。

## 六、完整参数模型：为什么初值和终值都是全 1

同一个"CRC-32"名称下其实有一族变体，差异由 6 个参数完全描述（业内称 Rocksoft 模型）：

| 参数 | 含义 | zlib 风格 CRC-32 的取值 |
|---|---|---|
| width | CRC 位宽 | 32 |
| poly | 生成多项式 | 0x04C11DB7（反射实现用 0xEDB88320） |
| init | 寄存器初值 | 0xFFFFFFFF |
| refin/refout | 输入/输出是否反射 | true / true |
| xorout | 输出异或值 | 0xFFFFFFFF |

初值与终值取全 1（而非全 0）的原因有两个，都来自同一个尴尬场景——**全零消息**：

1. 若 init = 0：消息全零 → 余数全零 → CRC 为零。"什么都没发"和"发了一串零"产生相同校验值；
2. 更隐蔽的是**前导零**：init = 0 时，消息开头任意长的一段零不参与任何计算（寄存器保持零），错误发生在前导零段内完全不可见。

init 与 xorout 的双重取反，使得零消息得到非零 CRC、前导零也有贡献——这两个"显然应该能查出来"的场景被堵死。

## 七、工程加速：从 1 bit/步 到 1 字节/周期

教科书实现是逐位的（每步处理 1 bit），工业界有一条清晰的加速阶梯，共同根基是 CRC 的**线性性**：

> 模 2 除法对 XOR 满足分配律——"先混合再除"可以拆成"分别除再异或"。

- **逐位**：1 bit/迭代。直觉版实现，~每字节 8 次循环。
- **查表法（1 字节/迭代）**：输入的一个字节有 256 种取值。利用线性性，"当前寄存器 + 该字节"对余数的影响可以**预先算好 256 种情况**存进表里；运行时一次查表 + 一次 XOR 完成一个字节。快约 8 倍，代价是 1KB 的表。
- **多表切片（slicing-by-8/16）**：查表法的推广——用 8 张表并行处理 8 个字节的贡献，每周期吞吐 8 字节。
- **硬件指令（SSE4.2 CRC32C）**：Intel 在微码里直接实现一个特定多项式的 CRC 计算，单指令处理 8 字节，每周期可发射一条。比软件查表快一个数量级。

注意这条阶梯的每一级都**不改变数学结果**——查表版、切片版、硬件版与逐位版产出完全相同的余数，加速只发生在"怎么把同样的数学算得更快"。

## 八、CRC-32 vs CRC-32C：存储系统为什么换多项式

RocksDB、ext4、Btrfs、iSCSI 用的都不是经典的 CRC-32（0x04C11DB7），而是 **CRC-32C（Castagnoli，0x1EDC6F41，反射 0x82F63B78）**。两个硬理由：

**① 硬件指令只实现了 C**。SSE4.2 选定 Castagnoli 多项式做硬件实现（选择时它已被 Koopman 的研究证明在目标消息长度上检测特性优异）。想吃到硬件加速，就得用 C。

**② 检测特性在"存储尺寸"上更优**。衡量错误检测的指标是**汉明距离（HD）**：错误多项式与"合法 CRC 倍数"的最小碰撞距离，HD=4 意味着 3 位以内任意错误 100% 检出。Koopman 的系统对比显示：

- 经典 CRC-32（HDLC 多项式）：HD=4 只维持到约 8KB 消息量级，更长消息退化为 HD=3；
- CRC-32C：HD=4 维持到约 2³¹ 位（数百 MB）量级。

存储系统的校验对象是 4KB block、64KB SST 块、MB 级对象——正好落在 C 的优势区。iSCSI 当年选 C 的论文论证（Sheinwald 等，2000）针对的正是 512B~2KB 的存储块尺寸。

一句话：**C 检测更强，还有免费硬件加速，存储界没有理由拒绝**。

## 九、可组合性：一个高级但重要的应用

CRC 的线性性还有一个不显然的推论——**分段计算可以合并**：

> 若知道 A 段的 CRC 值和长度、B 段的 CRC 值和长度，可以在**不重新扫描数据**的前提下，直接算出 A‖B 拼接后的 CRC。

代数直觉：A 段的整体贡献可以"折叠"成一个等价的短多项式，与 B 的余数做一次运算即可。这个性质支撑了几类真实系统：

- **零拷贝校验**：数据在内核/网卡分多段缓冲区时，各段分别 CRC 再合并，无需先拷贝成连续内存；
- **远端合并**：分布式系统里不同节点各持有一段数据，中心节点只交换 (CRC, 长度) 两个小值即可校验整体一致，不用搬数据；
- RocksDB 提供了对应的 `crc32c::Combine` 接口，用于分片校验的合并场景。

代价是默认 CRC **不感知数据位置**：若两个等长段的内容被互相交换，CRC 不会变——校验的是"内容"，不是"这块数据在不在它该在的位置"。对"数据写错位置"这类错误，一些文件系统的做法是把块的物理地址掺入校验计算（作为初值的一部分），让校验绑定"内容 + 位置"二元组。默认 CRC 只负责内容正确性，位置正确性由布局元数据负责。

## 十、选型对照：CRC 在校验光谱中的位置

| 方案 | 速度 | 随机错误检测 | 对抗性篡改 | 典型用途 |
|---|---|---|---|---|
| 异或/加法 checksum | 极快 | 弱（交换律：两字节互换不检！） | 无 | 嵌入式玩具、UDP 伪头 |
| Adler-32 / Fletcher | 快 | 中（短消息弱） | 无 | zlib 内部（历史选择） |
| CRC-32/C | 快（硬件极快） | 强（代数保证，HD=4） | 无 | 存储校验、网络 FCS |
| xxHash 等非密码哈希 | 极快 | 好（统计性，无代数保证） | 无 | 哈希表、去重、分片路由 |
| SHA-256 | 慢 1~2 个数量级 | 极强 | **有** | 签名、完整性认证 |

选型一句话：**非对抗的随机错误用 CRC（有代数保证），对抗场景用 SHA（有安全保证），纯哈希用途用 xxHash（只要散列均匀）**。第 1 篇思考题埋的"恶意篡改"问题，答案就是最后一行。

## 十一、自测与延伸

想验证自己实现的 CRC-32 是否正确，业界有万能测试向量：输入字符串 `"123456789"`（9 字节，不带换行），标准 zlib 风格 CRC-32 输出必为 `0xCBF43926`。任何 CRC 实现的第一次握手都从它开始。

延伸阅读（按深度排序）：

- Koopman & Chakravarty, *Cyclic Redundancy Code (CRC) Polynomial Selection for Embedded Networks*（2004）——多项式选型的定量研究，"选 C"的科学依据
- Sheinwald et al., *iSCSI CRC Considerations*（2000）——存储块尺寸下的 CRC 对比实证
- Williams, *A Painless Guide to CRC Error Detection Algorithms*——著名的"无痛 CRC 教程"，参数模型（Rocksoft Model）的出处
